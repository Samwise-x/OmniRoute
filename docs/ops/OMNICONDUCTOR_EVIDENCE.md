# OmniConductor acceptance evidence — follow-up

**Final status: NO-GO for full acceptance.** The previously identified exact capability-pairing, test-evidence, Faro action, result visibility, and Runner readiness gaps have been corrected and the local service verification passes. Two required external checks remain blocked: this execution environment has no container engine or Docker socket, and it has no provider API credentials. No real provider-backed coding task or Docker image build is claimed.

## Corrections delivered

- **Exact CLI/model pairing:** Hub eligibility now evaluates the requested model against the _same_ CLI capability. Runner-side harness choice independently verifies this pair. `RUNNER_<PROFILE>_MODELS` can pin models per harness, with the runner-wide model list as fallback. A regression test reproduced and fixed the Hub bug where a model from another CLI profile incorrectly made a runner eligible.
- **Real repository test evidence:** after a successful agent process, Runner auto-detects a declared `npm test`, or supported pytest setup; `RUNNER_TEST_COMMAND` accepts a JSON argv override. Tests have a distinct timeout. Manifests report `passed`, `failed`, `skipped`, or `not_run`, command, exit code, duration and bounded output. A detected test failure fails the task. The integration fixture executes a real `npm test` against the agent's change.
- **Retained results:** Hub stores bounded binary patches, worktree status, agent output and structured test outcomes. Authenticated task detail and the dashboard display patch/test evidence. The UI no longer suggests fetching a local branch that was never pushed.
- **Faro:** create/cancel requests require a signed, expiring confirmation token; invalid tokens do nothing. Open-ended chat can use OmniRoute's OpenAI-compatible model endpoint with a bounded Hub evidence snapshot. Hub-backed deterministic task/fleet answers remain the fallback. No action is delegated to the model.
- **Restart/drain correctness:** every Runner process registers a fresh session ID. Re-registering the same logical runner after a process restart clears its stale active count and requeues its previously claimed work immediately; heartbeats, claims and results from the old session are rejected. Graceful shutdown sets `draining`, continues lease heartbeats, and finishes active tasks without taking new claims.
- **Readiness:** Hub, Faro and Runner have Compose health checks. Runner `/readyz` requires successful registration and recent Hub contact. Pinned agent package versions, a service-context `.dockerignore`, and per-service configuration are present.

## Remaining requirements before GO

1. On a Docker-capable host, build the pinned images and start the documented Compose deployment. Observe Hub, Faro and both Runner health/readiness; connect OmniRoute to the same network/config; restart without deleting the persistent volume and verify history.
2. With authorized credentials, run real tasks through Claude Code, Codex and OpenCode against a disposable repository. Record each task ID, actual runner/model pairing, real test output, and retained patch. Provider login/configuration and model availability are deployment-specific.
3. Resolve or formally accept the dashboard-wide typecheck's 307 unrelated diagnostics, then require a clean dashboard typecheck for a full GO.
4. The runtime remains intentionally single-Hub/single-process with plaintext JSON state and one shared bearer secret; lease recovery is at-least-once. Keep the state volume protected and do not expose the services publicly without network/TLS controls and scoped credentials.

**Decision: NO-GO.** Implementation and local production-path tests now cover the previously identified software gaps, but this sandbox cannot prove image builds, healthy Compose startup, or real authorized vendor-agent execution. Those are still mandatory acceptance evidence.
